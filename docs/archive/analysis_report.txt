# ClipApp Database Query Patterns & Schema Analysis

Analysis Date: March 27, 2026
Codebase Size: ~1,419 lines of endpoint code + migrations + models
Database Type: PostgreSQL with SQLAlchemy Async ORM

==============================================================================
EXECUTIVE SUMMARY
==============================================================================

This analysis reveals 6 CRITICAL ISSUES and 8 PERFORMANCE CONCERNS:

CRITICAL ISSUES:
1. Table Naming Mismatch - Models use plural, migrations use singular (SCHEMA BROKEN)
2. Type Mismatches - Enum columns stored as String instead of ENUM
3. Column Type Mismatches - ID columns String in DB vs Integer in models
4. Missing Column - streamer_id missing in user_streamer table
5. Deprecated ORM Pattern - Using .from_orm() instead of .model_validate()
6. Foreign Key Inconsistencies - FK constraints don't match actual column types

PERFORMANCE ISSUES:
1. N+1 Query Problem - No batch loading of follows in sync endpoint
2. Missing Indexes - No indexes on foreign keys in votes table
3. Full Table Scans - Vote counting without optimization
4. Unnecessary Joins - Eager loading may cause over-fetching
5. Inefficient Vote Counting - Multiple COUNT queries per request
6. No Query Result Caching - Same data fetched repeatedly
7. Unoptimized Leaderboard - No pagination, loads all scores
8. JSON Storage Without Indexing - Edit history/chat stored as Text without JSONB

SECTION 3: N+1 QUERY PROBLEMS
==============================================================================

PROBLEM 1: Following Sync (following.py, lines 146-180)

Current Code Pattern:
for follow in follows:  # Could be 100+ follows
    existing = await db.execute(
        select(UserStreamer).where(
            UserStreamer.user_id == current_user.id,
            UserStreamer.streamer_id == follow["to_id"],
        )
    )
    if not existing.scalar_one_or_none():
        streamer = UserStreamer(...)
        db.add(streamer)
await db.commit()

Queries Executed:
- 1 query to get follows (external Twitch API)
- N queries to check existing (N = number of follows, typically 50-100)
- Total: N+1 queries

OPTIMIZED PATTERN (batch fetch):
existing_ids = await db.execute(
    select(UserStreamer.streamer_id).where(
        UserStreamer.user_id == current_user.id,
        UserStreamer.streamer_id.in_([f["to_id"] for f in follows])
    )
)
existing_set = set(row[0] for row in existing_ids)

for follow in follows:
    if follow["to_id"] not in existing_set:
        streamer = UserStreamer(...)
        db.add(streamer)
await db.commit()

Result: Reduces N+1 to 2 total queries

PROBLEM 2: Vote Aggregation (votes.py, lines 80-85)

Current Code:
likes_count = await db.execute(
    select(func.count(Vote.id)).where(
        Vote.clip_id == clip.id, Vote.vote_type == VoteType.LIKE
    )
)
current_score = likes_count.scalar() or 0

Issues:
1. Count query scans all votes then filters by type
2. Gets leaderboard from AppState (separate from DB)
3. State and DB can diverge

Optimization:
- Create partial index on (clip_id) WHERE vote_type = 'like'
- Or cache result with TTL
